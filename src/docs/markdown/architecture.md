架构
====

Caddy 是一个单一、自包含、无外部依赖的静态二进制文件，因为它是用 Go 编写的。这些价值观构成了项目愿景的重要部分，因为它们简化了部署，并减少了生产环境中繁琐的故障排查工作。

如果没有动态链接，那它如何扩展？Caddy 拥有新颖的插件架构，使其功能远超其他任何 Web 服务器，即使是那些带有外部（动态链接）依赖的服务器。

我们“减少活动部件”的理念最终带来了更可靠、更易管理、成本更低的网站——尤其是在大规模场景下。这份半技术性文档描述了如何通过软件工程实现这一目标。


## 概述

Caddy 由命令、核心库和模块组成。

**命令** 提供了你熟悉的[命令行界面](/docs/command-line)。它让你能够从操作系统中启动进程。这里的代码和逻辑量相当少，只包含以用户期望方式引导核心所需的部分。我们特意避免使用标志和环境变量进行配置，除非它们涉及引导配置。


<aside class="tip">

模块可以向命令行界面添加子命令！例如，这就是 [`caddy file-server`](/docs/command-line#caddy-file-server) 命令的来源。这些添加的命令可以拥有任意标志或使用任何环境变量，即使核心 Caddy 命令尽量减少其使用。

</aside>


**[核心库](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc)**，或称 Caddy 的“核心”，主要负责管理配置。它可以 [`Run()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Run) 一个新配置，或 [`Stop()`](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Stop) 一个正在运行的配置。它还提供了各种工具、类型和值供模块使用。

**模块** 负责其他一切。许多模块是 Caddy 内置的，被称为_标准模块_。这些模块被认为对大多数用户最有用。


<aside class="tip">

有时术语 *模块*、*插件* 和 *扩展* 可以互换使用，通常没问题。从技术上讲，所有模块都是插件，但并非所有插件都是模块。模块特指一种扩展 Caddy [配置结构](/docs/json/) 的插件。

</aside>




## Caddy 核心

在核心层面，Caddy 仅加载一个初始配置（“config”），如果没有配置，则打开一个套接字以便稍后接收新配置。

一个 [Caddy 配置](/docs/json/) 是一个 JSON 文档，顶层包含一些字段：

```json
{
	"admin": {},
	"logging": {},
	"apps": {•••},
	...
}
```

Caddy 核心原生支持部分字段：

- [`admin`](/docs/json/admin/)：用于设置[管理 API](/docs/api) 并管理进程
- [`logging`](/docs/json/logging/)：用于[输出日志](/docs/logging)

但其他顶层字段（如 [`apps`](/docs/json/apps/)）对 Caddy 核心来说是不透明的。实际上，Caddy 对 `apps` 中的字节所做的全部工作就是将其反序列化为一个接口类型，该接口类型上可以调用两个方法：

1. `Start()`
2. `Stop()`

仅此而已。当加载配置时，它会调用每个应用的 `Start()`；当卸载配置时，它会调用每个应用的 `Stop()`。

当应用模块启动时，它会启动该应用的模块生命周期。


<aside class="tip">

如果你是构建 Caddy 模块的程序员，可以在我们的 [扩展 Caddy](/docs/extending-caddy) 指南中找到类似信息，但更侧重于代码。

</aside>


## 模块生命周期

有两种类型的模块：_宿主模块_ 和 _客体模块_。

**宿主模块**（或“父”模块）是加载其他模块的模块。

**客体模块**（或“子”模块）是被加载的模块。所有模块都是客体模块——甚至应用模块也是。

模块经过加载、配置和验证、使用、清理，顺序如下：

1. 加载
2. 配置和验证
3. 使用
4. 清理

当加载配置时，Caddy 通过初始化所有配置的应用模块来启动模块生命周期。此后，每个应用模块会继续完成剩余工作，就像“层层嵌套的乌龟”一样。

### 加载阶段

加载模块涉及将其 JSON 字节反序列化为内存中的类型化值。基本就是这样。它只是将 JSON 解码为值。

### 配置阶段

这个阶段是大部分设置工作发生的地方。所有模块在加载后都有机会进行自我配置。

由于 JSON 编码中的任何属性都已经解码，此处只需进行额外的设置。配置阶段最常见的任务是设置客体模块。换句话说，配置宿主模块也会导致配置其客体模块，层层向下。

通过浏览[我们文档中的 Caddy JSON 结构](/docs/json/)，你可以了解这一点。任何出现 `{•••}` 的地方都表明可能使用客体模块；当你点击进入时，可以继续向下探索，直到没有更多的客体模块。

其他常见的配置任务包括设置模块生命周期内将使用的内部值，或标准化输入。例如，[`http.matchers.remote_ip`](/docs/modules/http.matchers.remote_ip) 模块在配置阶段解析来自 JSON 输入的 CIDR 值。这样，它就不需要在每个 HTTP 请求期间都进行解析，从而提高了效率。

验证也可以发生在配置阶段。如果模块的最终配置无效，可以在此处返回错误，从而中止整个配置加载过程。

### 使用阶段

一旦客体模块被配置和验证，它就可以被其宿主模块使用。具体含义由每个宿主模块决定。

每个模块都有一个 ID，由命名空间和该命名空间中的名称组成。例如，[`http.handlers.reverse_proxy`](/docs/modules/http.handlers.reverse_proxy) 是一个 HTTP 处理器，因为它位于 `http.handlers` 命名空间中，其名称是 `reverse_proxy`。`http.handlers` 命名空间中的所有模块都满足宿主模块所知的相同接口。因此，`http` 应用知道如何加载和使用这些类型的模块。

### 清理阶段

当需要停止配置时，所有模块都会被卸载。如果模块分配了需要释放的资源，它有机会在清理阶段进行释放。


## 插件接入

一个模块——或任何 Caddy 插件——通过为模块包添加 `import` 来“接入”Caddy。通过导入包，[模块向 Caddy 核心注册自身](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#RegisterModule)，这样当 Caddy 进程启动时，它就能按名称识别每个模块。它甚至可以在模块值和名称之间建立关联，反之亦然。


<aside class="tip">

无需修改 Caddy 代码库即可添加插件。[自述文件](https://github.com/caddyserver/caddy/#with-version-information-andor-plugins)中有相关说明！

</aside>


## 管理配置

在高并发和服务器所需数千个参数的情况下，更改正在运行的服务器的活动配置（通常称为“重载”）可能很棘手。Caddy 通过一种具有许多优点的设计巧妙地解决了这个问题：

- 不中断运行中的服务
- 支持细粒度的配置更改
- 仅需一个锁（后台）
- 所有重载都是原子性的、一致的、隔离的，并且大部分是持久的（“ACID”）
- 全局状态最小化

你可以[在此处观看关于 Caddy 2 设计的视频](https://www.youtube.com/watch?v=EhJO8giOqQs)。

配置重载通过配置新模块工作，如果全部成功，则清理旧模块。在短暂的时间内，两个配置同时运行。

每个配置都与一个[上下文](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#Context)相关联，该上下文保存所有模块状态，因此大多数状态不会逃逸出配置的范围。这对正确性、性能和简单性来说是个好消息！

然而，有时确实需要全局状态。例如，反向代理可能会跟踪其上游的健康状况；由于每个上游在全局中只有一个，如果每次进行微小配置更改时忘记它们，那就不好了。幸运的是，Caddy[提供了类似语言运行时垃圾回收器的工具](https://pkg.go.dev/github.com/caddyserver/caddy/v2?tab=doc#UsagePool)来保持全局状态整洁。

一种明显的在线配置更新方法是同步访问每一个配置参数，即使在热路径中也是如此。这在性能和复杂性方面极其糟糕——尤其是在大规模场景下——因此 Caddy 不使用这种方法。

相反，配置被视为不可变的原子单元：要么整体替换，要么不做任何更改。[管理 API 端点](/docs/api)——允许通过深入结构进行细粒度更改——仅修改配置的内存表示，然后从中生成并加载一个全新的配置文档。这种方法在简单性、性能和一致性方面具有巨大优势。由于只有一个锁，Caddy 很容易处理快速重载。
